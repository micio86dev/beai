# Tasks: The Candidate Interview Screen Becomes A Work Video Call

Strict TDD: every behaviour task is a RED step (a failing test, observed failing for the stated reason) followed by a
GREEN step (the smallest change that makes it pass), then REFACTOR with the suite green. A box is ticked only for an
observed outcome, with the commit sha next to it. Inputs: `proposal.md`, `design.md`, `specs/interview-frontend/spec.md`.
Created 2026-10-09 from the code at `frontend` `f1769a7` (release 0.24.0) and wrapper `develop` `4c5b72e`. Nothing here is
implemented.

## Rules for every slice

- **Review budget.** About **400 authored changed lines per slice, tests and docs included** (additions plus deletions).
  It is a planning heuristic, not a hard cap: if the correct solution is larger, say why in the PR and continue; never
  delete blank lines or comments, omit tests, minify or split artificially to fit. **Excluded from the count and stated as
  such in each PR:** Playwright screenshot baselines (generated by `task e2e:update`), `bun.lock`, and any file produced by a
  command rather than written by hand. Deletion-only slices (`UI-13`) are counted but reviewed as a removal.
- **Commits.** One Conventional Commit per work unit on a `feature/*` branch (Git Flow), tests and docs alongside the
  behaviour, no AI attribution, never `--no-verify`, never a push from a worker. Push, PR and merge stay with the owner.
  Code slices are commits in the `frontend` submodule; the wrapper pointer is bumped once, when the owner releases `frontend`
  (SemVer `M.m.p` plus the `VERSION` file at `release/*`, never per slice).
- **Flag and darkness.** Every behaviour is behind `candidateCallUi` (default off) until `UI-12`. With the flag off, the
  existing unit and E2E specs MUST pass unchanged; a slice that needs to edit one of them is wrong, except `UI-12`.
- **frontend commands (Bun only).** Per file: `cd frontend && bun run test:unit -- tests/unit/<file>.spec.ts`. Before a PR:
  `bunx nuxi prepare && bun run typecheck`, `bun run lint`, `bun run format:check`, `bun run test:unit:coverage` (thresholds
  lines 85, branches 88, functions 90). Every user-visible string needs `it` and `en` (`i18n-interview-keys.spec.ts` stays
  green). Playwright only through `task e2e:frontend` (the pinned container, chromium and webkit); baselines only through
  `task e2e:update`. Never `npm`, `npx`, `pnpm` or `yarn`.
- **No new dependency.** If a slice believes it needs one, it stops and reports (Dependency Resolution Policy).
- **TDD mode.** Strict TDD on; runners are Vitest (frontend) and Playwright (E2E). Run unit specs one at a time and the
  full suite once per slice; never start a build beside a test run (the local Docker VM is 4 GB).
- **Delegation route.** Each slice is delegated-direct work: one writer per slice, reading that prepares the write belongs to
  the writer. No SDD phase workers. Record the route per slice in the PR.
- **Review gate.** Where receipt-driven development is enabled by the owner, the native review candidate is a work-unit
  commit or a PR slice, never a checkbox and never the accumulated branch.
- **Coordination.** `tavus-single-session-interview` also edits `useInterviewSession.ts`, `AvatarPlayer.client.vue` and
  `interview-frontend` requirements. Whichever merges second rebases. `UI-02` and `UI-09` are the slices that touch shared
  files; they re-read the file on `develop` before writing.

## Offline versus live

Everything below is provable with Vitest, Playwright route mocks and the mock provider, and is the merge gate. These claims
are **LIVE or MANUAL**, are not assumed true, and block no slice. Each needs the owner's separate go because it spends
provider credits or a person's time.

| Id | Claim | Why offline cannot prove it |
|---|---|---|
| M1 | With a real HeyGen avatar the ring follows `speaking`, and with a real Tavus avatar it follows the remote audio level | Real provider audio and events |
| M2 | A real avatar's finished utterance reaches the question band within an acceptable delay | Provider timing |
| M3 | NVDA (Windows, Chrome) and VoiceOver (macOS, Safari) read the question region, the boundary focus move, the dialog and the suspended screen once and in order | Real screen readers |
| M4 | A real browser camera frames acceptably in the bottom-right tile | Real camera |
| M5 | On a real two-competency interview the first avatar utterance of competency 2 is not a greeting, and the handover has no audible cut | Model and provider behaviour (feeds `T-BUG-1`/`T-BUG-2`) |

## T-BUG-1: Smooth handover between competencies (reserved slot)

Tester finding (a): "at the end of the first question the audio/video stopped unexpectedly and the move to the second question
was jerky." Depends on: `design.md` Appendix A (root cause and fix design, appended by the orchestrator). Independent of UI-01 to
UI-11: the fault is not specific to the new screen, so the tests run against both servers where the fix applies.

Acceptance (behaviour, from the spec requirement `A Competency Boundary Is A Smooth Handover`):

- the end phrase plays to completion before the outgoing session is silenced or released;
- no unexpected stop of audio or video, and no blank, frozen or skeleton frame, between the end phrase and the next competency's
  first utterance (documented slow-incoming fallback excepted);
- one visual transition, no layout shift of the stage or the question band;
- at most one avatar audible at any instant.

- [ ] T-BUG-1.1 RED: an E2E (mock provider, frame sampling as in the existing handover tests) and unit assertions encoding the four
      criteria above, observed failing for the reason Appendix A names. If a criterion cannot be reproduced offline, say so and record
      it under M5 instead of faking a pass.
- [ ] T-BUG-1.2 GREEN: the fix designed in Appendix A, within the review budget or with the reason stated.
- [ ] T-BUG-1.3 Verify: the new tests green on both servers where applicable; the existing `invisible-competency-handover` E2E cases
      and `interview-handover.spec.ts` unchanged and green. Commit: `fix(frontend): <scope named in Appendix A>`.
